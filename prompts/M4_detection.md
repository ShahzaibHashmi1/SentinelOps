CORRELATION (detector/app/correlator.py, pure logic, no I/O)
- Symptom key = (rule_id, subject). A symptom is created when its rule has fired continuously for for_s (first_seen = the first firing evaluation of that hold, so the delay is visible), is active while it fires, and becomes inactive when it stops (last_seen = last firing evaluation). A symptom that fires again inside the same incident is reactivated (flaps + 1), not duplicated. peak_value and last_value are kept.
- One incident is open at a time (the stack is one application). The first symptom with opens_incident true creates the incident; every later symptom, with any opens_incident value, attaches to it. Two independent faults at the same time therefore give one incident; document this as a tier 1 limitation.
- Resolve: an incident resolves when no symptom has been active for resolve_after_s (default 60) and both sources are ok during that time. A data gap pauses this timer (it never counts as quiet time).
- Reopen: a symptom that opens within reopen_within_s (default 120) after a resolve reopens the same incident (status open, resolved_at null, reopen_count + 1) instead of creating a new one. After that window a new incident is created. Both values are settings (environment variables) with these defaults.
- primary_service (deterministic): if no active or past symptom of the incident has role "load" and the symptoms with role "root_signal" all name ONE service, that service; otherwise null. Roles effect, dependency_effect, evidence never set it. candidate_services = services of all symptoms plus the dependency named in R06 details, ordered by first_seen then name. affected_services = all services of the symptoms. Expected consequence: F08 and F11 give primary_service null (metrics alone do not tell the caller from the dependency); that is accepted in tier 1.
- Severity = the highest severity among the symptoms. Title = a short deterministic text built from the first symptoms (no free text, no LLM).

INCIDENT FORMAT (fixed, schema_version 1; the API returns exactly this; document it with two full examples in docs/DETECTOR.md)
incident_id (string "INC-" plus a zero-padded sequence number from the database), schema_version, status ("open" or "resolved"), opened_at, updated_at, resolved_at (null while open), reopen_count, severity, title, primary_service (string or null), candidate_services, affected_services, symptoms (list: symptom_id, rule_id, detector, source, service (string or null), role, severity, opens_incident, first_seen, last_seen, active, flaps, comparator, threshold, peak_value, last_value, detail), data_gaps (list: source, start, end or null while open). All timestamps are UTC ISO 8601 with milliseconds and "Z", like the ground truth. opened_at is the time the incident was created (after the hold); first_seen of its first symptom shows when the signal started. M12 uses opened_at for MTTD.

NO-DATA AND WARM-UP (D59)
- Each cycle: Prometheus source ok only if GET /-/ready answers 200 and the query succeeds; Loki source ok only if GET /ready answers 200 (a 503 is no_data) and the query succeeds. A failed single query makes only that rule no_data; the error text goes to the log and the observation detail.
- no_data observations freeze the symptom (active flag and last_seen do not change), reset the hold counter of that rule, pause the resolve timer and are recorded in data_gaps. They never fire, never clear.
- After a source returns, it stays in "warming_up" for warmup_s (default 30): its observations are no_data. The same warm-up applies for the first warmup_s after the detector starts. The reasons: Prometheus has no series for a few seconds after a restart (a missing series must not read as a missing container), rate windows are not full, and Loki windows can still contain old lines.
- Known consequence to document: stopping or starting the whole stack is a real outage and opens an incident (R01, R02); an incident also stays open across a detector restart (it is read back from SQLite; hold counters are not persisted and restart from zero).

EVALUATION LOOP
Interval 5 s (setting EVAL_INTERVAL_S), one thread; HTTP timeout 3 s per query; a cycle never overlaps the next (skip and log if late); use time.monotonic for holds and datetime UTC for stored times; queries are sent as POST forms (like the handoff helpers) to http://prometheus:9090/api/v1/query and http://loki:3100/loki/api/v1/query; verify both ports and paths in the compose files. All settings come from environment variables with defaults (PROMETHEUS_URL, LOKI_URL, EVAL_INTERVAL_S, WARMUP_S, RESOLVE_AFTER_S, REOPEN_WITHIN_S, DB_PATH=/data/detector.db, LOG_LEVEL). Logs are JSON, one line per event, to stdout, with the same field names as the M1 services (ts, level, service, version, request_id null, event); keep it in your own small formatter.

STORE (detector/app/store.py)
SQLite file /data/detector.db: tables incidents, symptoms, data_gaps, meta (schema_version); PRAGMA journal_mode=WAL and a busy timeout; every write in one transaction per cycle; the API opens read-only connections (uri mode=ro) per request. API AND METRICS (detector/app/api.py, http.server ThreadingHTTPServer, port 9100, JSON UTF-8)
- GET /health: always 200 {"status": "ok", "service": "detector", "version": ...} (liveness only; used by the compose healthcheck, which must use python urllib because the image has no wget or curl).
- GET /ready: 200 when the evaluation loop finished a cycle within the last 3 intervals, otherwise 503. A source in no_data does NOT make the detector not ready.
- GET /internal/v1/status: sources (prometheus, loki: ok, no_data or warming_up, since, detail), last_cycle_at, cycle_duration_ms, rules_loaded, open_incident_id (or null), settings.
- GET /internal/v1/rules: the loaded rules (without secrets; there are none).
- GET /internal/v1/incidents?status=open|resolved&limit=1..200&since=<ISO ts>: newest first, full incident objects. GET /internal/v1/incidents/<incident_id>: one incident or 404.
- Any other method gives 405 with an Allow header; unknown paths 404; error body {"error": {"code": ..., "message": ...}}.
- GET /metrics (Prometheus text format, written by hand): detector_evaluation_cycles_total, detector_last_evaluation_timestamp_seconds, detector_evaluation_duration_seconds, detector_source_status{source} (1 ok, 0 not ok), detector_rule_state{rule_id,subject} (1 firing, 0 ok, -1 no_data), detector_incidents_open, detector_incidents_total, detector_query_errors_total{source}.
